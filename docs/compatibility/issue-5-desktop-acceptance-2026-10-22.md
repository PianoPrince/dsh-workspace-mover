3. 打开设置中的会话修复面板，点击“自检”。结果摘要末尾应显示 `v2.4.0-rc.1`。
4. 也可以在测试对话中要求“调用 mover_doctor，原样报告 pluginVersion 和失败项”。应返回 `2.4.0-rc.1`。如果版本不符，先停止验收并反馈。

`filesystem-fallback` 提示本身不是失败：宿主尚无公开的原始档案迁移接口。自检如有 `fail` 项，请提供具体项目与内容。

## 3. 已打开会话排队、重启迁移、继续发送

1. 在 A 新建测试会话，发送“迁移验收 A1，请只回复 A1 收到”，等待回复结束。
2. 将该会话拖到 B，确认迁移。预期：提示排队、等待释放写入句柄，可能需要重启；不能提示已经迁移完成。
3. 在原会话继续发送“A2，请只回复 A2 收到”。预期：正常回复，无旧路径写入报错。
4. 在 C 新建另一个测试会话，发送“重启停留页”。保持选中 C 的会话，再正常彻底退出 DSH。这样重启时不会自动打开待迁移的 A 会话、再次占用它的写入句柄。
5. 重启后先停留在 C，等待约 10 秒。在修复面板的迁移队列查看任务是否完成。等待期间不要打开待迁移会话。
6. 任务完成后，在 B 打开迁移会话，发送“B1，请只回复 B1 收到”。预期：正常回复，A1/A2 历史完整，没有重复会话。
7. 让 Agent 报告当前会话的有效工作目录。预期为 `E:\DeepSeekHarness\data\pr-review-20261022\acceptance\B`。
8. 再切换到 C，彻底退出并重启一次。确认会话仍在 B，再发送“B2，请只回复 B2 收到”。不应重复迁移、重复追加记录或出现旧目录错误。

如果任务一直等待，保留任务，提供自检结果和队列原因；不要手动移动 sessions 文件。

## 4. 工作区改名与审批

在普通权限模式下，让 Agent 使用 `mover_rename_workspace` 把 C 改名为 `WSM-C-1022-renamed`：

1. 第一次在审批框拒绝：名称必须保持不变。
2. 再次请求并批准：名称应更新，路径仍为 C，原会话可打开。
3. 改成 A 的已有名称：应直接拒绝，不弹一个注定失败的审批框。
4. 改成当前名称：应返回无需修改，不弹框。

在 DSH 的完全访问模式下，再把 C 改回 `WSM-C-1022`：应成功，插件不请求额外审批。切换权限模式属于宿主操作，如宿主另有确认按其提示处理。

审批服务缺失时，普通模式改名、迁移和修复工具必须拒绝执行，提示使用面板；不要求你卸载服务，这条由自动检查覆盖。登记已有目录无需审批；完全访问免审批仅适用于改名，未放宽原有迁移/修复审批。

## 5. 自动滚动

已有工作区足够多、侧栏出现滚动条时直接验证。如果不足，可让 Agent 使用 `mover_create_workspace`，登记验收目录下 `scroll-01` 到 `scroll-12` 的已有目录，名称设为 `WSM-scroll-01` 到 `WSM-scroll-12`。

1. 拖动专用测试会话，指针停在侧栏底部边缘。预期：持续向下滚动，能够看到原先在视口外的工作区。
2. 移到侧栏顶部：应向上滚动；移到中间、侧栏之外、松手或取消拖动：应停止。
3. 到达最顶部/最底部后应稳定停止，不抖动。
4. 实际投放一次：确认框目标应与投放工作区一致；已打开会话仍按第 3 节排队。

插件卸载时取消滚动动画由自动 DOM 检查覆盖，无需你反复卸载插件。
